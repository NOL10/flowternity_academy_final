# Profile Isolation in Performance PDF Export

The performance PDF export now surfaces the active child's name as the athlete identifier instead of the parent's name, adding profile-specific context to the filename and ensuring multi-child households can distinguish their children's reports. The export validates that a child profile is selected before proceeding and includes parent context in the footer for administrative clarity.

**Watch for:** The generatePerformanceReportPDF function signature still expects a playerName parameter but gets no visibility into whether this is a parent or child profile. The PDF footer is static and doesn't include parent context as proposed. The filename improvement isn't implemented yet. Verify that all proposed changes were actually applied before shipping.

**Verdict**: NEEDS_CHANGES

---

## High-level view

The core fix addresses a real usability gap: when a parent with multiple children exports a performance report, the PDF and filename now identify which child's data it contains, avoiding silent confusion when multiple reports land in the same folder. The change switches the playerName passed to the PDF generator from `user?.full_name` (the logged-in parent) to `activeChild?.athlete_name || activeChild?.child_name` (the selected child).

The export now guards against exporting when no child is selected by checking `activeChild` upfront, which prevents orphaned reports with unclear context. The filename format moves from `performance-{sport}-{date}.pdf` to include the child identifier for document traceability.

The PDF footer presently has no parent-context additions. The proposed change to include parent name or role in the footer for administrative auditing hasn't been woven into the generatePerformanceReportPDF function yet, and would require a parameter addition or refactor.

## Details

<details>
<summary>Details</summary>

### Player Name Mismatch in Multi-Child Households

Line 120 passes `user?.full_name` to the PDF generator. In a multi-child household, this is the parent's name, not the child's. Every child's PDF displays the parent as the athlete, which defeats multi-profile support. The fix:

```javascript
// Current:
const doc = await generatePerformanceReportPDF(
  user?.full_name || 'Player',
  ...
);

// Proposed:
const doc = await generatePerformanceReportPDF(
  activeChild?.athlete_name || activeChild?.child_name || 'Player',
  ...
);
```

The PDF header already renders the playerName at line 39 in performance-pdf.js, so switching to the active child's name surfaces the correct athlete identity immediately.

### Missing Profile Selection Guard

The exportPerformance function validates `performanceData` and `sport` on lines 106–109 but not `activeChild`. If activeChild becomes null (e.g., a deleted profile between page loads), the export proceeds with stale or orphaned data. The activeChild state drives the data fetch at line 75, so the guard is essential for consistency:

```javascript
if (!activeChild) {
  toast.error('Select a child profile first');
  return;
}
```

This is a **confirmed** issue — the activeChild state is the authoritative scope for all performance data on this page.

### Filename Lacks Child Identifier

Line 127 saves as `performance-${activeSport}-${date}.pdf`. In a multi-child household, files for different children with the same sport and export date overwrite each other. Include the child's name:

```javascript
const childIdentifier = activeChild.athlete_name || activeChild.child_name || activeChild.id;
const sanitizedName = childIdentifier.replace(/\s+/g, '-').toLowerCase();
doc.save(`performance-${sanitizedName}-${activeSport}-${new Date().toISOString().split('T')[0]}.pdf`);
```

This surfaces the child's identity in the filename without manual renaming and prevents silent file overwrites.

### PDF Footer Missing Parent Context

The performance-pdf.js footer (lines 118–121) renders only "Generated by Flowternity Academy" with timestamp. For administrative auditing, include the child's profile name and parent account holder. This requires passing a parentName parameter to generatePerformanceReportPDF and updating the footer:

```javascript
doc.text(
  `Report for ${playerName} • Parent: ${parentName || 'N/A'} • Generated ${new Date().toLocaleDateString('en-IN')}`,
  margin,
  pageHeight - 10
);
```

This is a **likely** concern for audit trails if PDFs are shared between parents and admins, though optional if reports are child-facing only. The current code doesn't implement this yet.
